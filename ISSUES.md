# Issues Log

Findings from a piece-by-piece pre-ship review of the codebase. Grouped by review section.

## Priority Ranking

All 25 issues below, ranked by severity. `§N.M` refers to item M in section N further down this file.

### Critical — ship-blocking

1. **§3.1 — `create_run` never checks workspace membership.** Any authenticated user can inject runs into an arbitrary workspace, poisoning another tenant's run list and burning their cost budget, and can pull another workspace's uploaded documents into the run via unchecked `doc_ids`. Straightforward cross-tenant data/cost exploit with no auth bypass required. **✅ Fixed (`90967d1`).**
2. **§3.2 — `/analytics/metrics` and `/costs` are global, unscoped aggregates.** Any logged-in user sees platform-wide spend, per-agent cost, and quality scores across every tenant. Cross-tenant data leak with no auth bypass required. **✅ Fixed (`a6aa090`).**
3. **§5.1 — The HITL 3-stage gate doesn't actually stop the LangGraph supervisor.** The graph has no interrupt points, so each `.invoke()` runs end-to-end; the "approve research" screen shows output that's already been analyzed, reviewed, drafted, and edited behind the scenes, and later stages silently redo ~2x the LLM work. This defeats the core human-in-the-loop feature the product is built around. **✅ Fixed (`965a91b`).**
4. **§9.1 — Langfuse integration calls a nonexistent API and will crash every run once enabled.** `lf.trace()`/`trace.span()` don't exist in the pinned v4 SDK. Dormant only because the documented "set these two env vars" upgrade path hasn't been exercised — the first person who follows `.env.example`'s own instructions takes down every run in the app. **✅ Fixed (`1f7041a`).**
5. **§4.1 — Cost tracking always logs `$0.00`.** `_log_token_usages` hardcodes `total_cost=0.0` for every call; there's no pricing table at all. The cost/analytics feature is completely non-functional, not just inaccurate. **✅ Fixed (`aec1809`).**
6. **§8.1 — Citation extraction returns empty for essentially every real run.** `extract_citations` only parses the internal RAG string format, never the Markdown-link format every prompt actually instructs agents to produce. Citations surfaced to the frontend and analytics are empty for the primary web-search-driven path. **✅ Fixed (`c6f6ad5`).**

### High — security or core-feature correctness, bounded impact

7. **§2.1 — `assert_run_access` ignores workspace role entirely.** A `"viewer"` member can approve/resume a HITL-gated run with an arbitrary instruction, same as an admin. Privilege escalation, but bounded to members already inside the workspace (vs. the cross-tenant issues above). **✅ Fixed (`376e7ba`).**
8. **§7.1 — The entire `formatters/` package is dead code.** A run created with `format="linkedin"` downloads as raw Markdown (`[text](url)`, `#` headers) instead of LinkedIn-safe plain text — an advertised output format ships broken. **✅ Fixed (`1847de1`).**
9. **§8.2 — `SearxngSearchTool`/`TavilySearchTool` share the cache key `"web_search"`.** Toggling `SEARXNG_URL` — the flagship feature of this change — can silently serve one provider's cached results under the other for up to 7 days. **✅ Fixed (`8d99c2e`).**
10. **§1.1 — A real 64-char SearXNG `secret_key` is committed to git.** Works today as a default but is exactly the kind of checked-in secret that ships to prod by accident. **✅ Fixed (`cdb9b85`).**

## 3. Backend API surface

1. **`backend/routers/runs.py:16-35` `create_run` never checks workspace membership.** Compare with `upload_file` (`backend/routers/upload.py:26-28`) and `list_runs` (`runs.py:47-50`), which both correctly look up `WorkspaceMember` before touching workspace-scoped data. `create_run` takes `body.workspace_id` straight from the request body and stores it on the new `Run` with no membership check. Any authenticated user can create a run under an arbitrary workspace UUID — it appears in that workspace's run list to its real members (data injected into someone else's workspace) and burns LLM/search/scrape costs attributed to that workspace. The same request also accepts `doc_ids` with no check that the referenced documents belong to the caller or that workspace, so a crafted request could pull another workspace's uploaded PDF content into the run.

   **✅ Fixed (`90967d1`).** `create_run` now checks `WorkspaceMember` membership before creating the run (403 if not a member), and validates every `doc_id` resolves to a `Document` in the target workspace (403 otherwise). Regression tests added in `test_access_control.py`.

2. **`backend/routers/analytics.py` `/metrics` and `/costs` are global, unscoped aggregates.** Both endpoints require `get_current_user` but then aggregate across *every* run and *every* cost row in the database — not filtered by `user_id` or workspace membership. Any logged-in user can see platform-wide token spend, per-agent cost breakdown, and quality scores across all tenants. Inconsistent with every other router, which scopes results to the caller's own runs/workspaces.

   **✅ Fixed (`a6aa090`).** Added a `_scope_to_caller` helper: scopes to `Run.workspace_id` (after checking membership) when a workspace is requested, otherwise falls back to `Run.user_id`. Applied to both `/metrics` and `/costs`. Regression tests added in `test_analytics.py`.

## 5. Agents (core product logic)

1. **The 3-stage HITL orchestration doesn't match how the LangGraph supervisor actually executes — the graph runs end-to-end on every `.invoke()`, with no pause points.** `backend/services/run_service.py` calls `supervisor.invoke()` three times, expecting each call to stop after one stage (research → human approval → analysis → human approval → write). But `backend/agents/crew.py`'s compiled graph has no `interrupt_before`/checkpointer configured (confirmed via repo-wide grep — none exists), so each `.invoke()` runs to `END`:
   - Call 1 (meant to stop after "research"): `route_entry` → `"plan"` → `"research"` → `route_after_research` unconditionally continues to `"analyse"` (`crew.py:195-199`) → `"review"` (unconditional edge, `crew.py:262`) → `route_after_review` can loop back to `"research"` up to 3x on FAIL (`crew.py:228-229`) → eventually `"write"` → `"edit"` → `END`. The user's first HITL approval screen shows research output that has *already* had analysis, quality review (with possible silent retries), drafting, and editing run against it using empty feedback — the gate does nothing to stop that work from happening.
   - Call 2 (meant to run only "analysis"): built from the fully-populated end state of call 1 with just `analysis_output` reset to `""`. `route_entry` sends it back into `"analyse"` → auto-continues to `"review"` → can send it back to `"research"` again (re-running a stage the user already approved) before reaching `"write"` → `"edit"` → `END` again.
   - Only call 3 (final write) happens to align correctly, since `analysis_output` is non-empty and `route_entry`'s first check sends it straight to `"write"`.
   Net effect: every run does roughly 2x the intended LLM work (a full write+edit pass from call 1 is silently discarded and redone in call 2), and review-triggered retries can re-run "research" invisibly after the user already approved it. Compounds directly with the always-zero cost tracking bug (Backend services #1) — actual spend per run is both miscounted and higher than intended.

   **✅ Fixed (`965a91b`).** The compiled graph in `crew.py` now uses a real `InMemorySaver` checkpointer with `interrupt_before=["analyse", "write"]`, so execution genuinely pauses at each gate. `run_service.py`'s stage orchestration was rewritten to resume the same checkpointed thread (`invoke(None, config)`/`update_state`) driven by `get_state().next`, instead of hand-rolling state between three independent `.invoke()` calls. A review-triggered research retry is now re-surfaced for approval instead of silently redone. Regression tests added in `test_crew_graph.py` (graph-level pause/resume/retry) and `test_run_service_hitl.py` (service-level stage gating).

2. **`backend/agents/publisher.py` (`publish_to_linkedin`, `publish_to_buffer`) is dead code with a broken config lookup.** It's never imported or called anywhere in the codebase (routers, services, or `crew.py`). Even if wired in, it can't work: it reads `getattr(settings, "LINKEDIN_ACCESS_TOKEN", None)` / `BUFFER_ACCESS_TOKEN` / `BUFFER_PROFILE_IDS`, but none of these are declared fields on `Settings` in `backend/config.py` (only documented in `.env.example:66-69`). Since `Settings.model_config = {"extra": "ignore"}`, pydantic-settings never loads them onto the `settings` object no matter what's in the environment, so `getattr` always falls through to `None` and the functions always return a "not configured" error.

   **✅ Fixed (`e4c7bf6`).** Deleted `publisher.py` and the orphaned `LINKEDIN_ACCESS_TOKEN`/`BUFFER_ACCESS_TOKEN`/`BUFFER_PROFILE_IDS` block from `.env.example`. No test coverage existed and nothing referenced it, so there was nothing worth fixing forward — this was pure V2 scaffolding that never got wired to a router.

The rest of the pipeline treats citations as load-bearing (reviewer's rubric explicitly scores "Citation Integrity," editor's backstory calls citations "a badge of authority"), so a LinkedIn-formatted run would ship with every source attribution silently dropped — should convert to `text (URL)` or move sources to a trailing list instead of deleting them.

## 8. Search/crawl tools

1. **`extract_citations` (`backend/tools/rag.py:184-194`) parses a citation format the LLM agents never actually produce for web research.** It regex-matches `"SOURCE: <file> (Page: <N>)"` — exactly and only the format `RAGTool._run` prints for internal-document search results (line 139). But every prompt governing actual output citations (`configs/prompts.yaml`'s researcher template, `agents/writer.py`'s "cite all sources using Markdown links") instructs Markdown-link citations (`[Title](URL)`), never the `SOURCE: ... (Page: ...)` string. Since `run_service.py` calls `extract_citations()` on that Markdown-formatted LLM output, it returns an empty list for essentially every web-search/scrape-driven run — the primary path. `metrics.citations` (surfaced to the frontend) and `analytics.py`'s `total_citations` aggregate are effectively always empty except for the rare document-grounded run whose final text happens to echo the internal RAG format verbatim.

   **✅ Fixed (`c6f6ad5`).** Added a second regex for `[Title](URL)`, restricted to `http(s)` targets so in-page anchors/relative links aren't misread as citations. Both formats are parsed and deduped together into the same `{"source", "page"}` shape (page = URL for Markdown-link citations), so no downstream changes were needed in `run_service.py`'s merge logic or the frontend. Regression tests added in `test_retrieval.py` covering Markdown-link parsing, dedup, non-http links being ignored, and mixed RAG+Markdown content in one document.

2. **`SearxngSearchTool` and `TavilySearchTool` share the literal cache key `name = "web_search"`** (`tools/search.py:11`, `:52`), and `tool_cache.get/set` keys purely on `(tool_name, query)` with no provider dimension. Toggling `SEARXNG_URL` on/off — exactly the feature this diff adds — means a query cached under one provider is silently served back under the other for up to the cache's 7-day TTL, even though the two backends can return meaningfully different result sets/freshness.

   **✅ Fixed (`8d99c2e`).** Both `_execute_search` methods now key `tool_cache.get/set` on a provider-scoped namespace (`"web_search:searxng"` / `"web_search:tavily"`) instead of the shared `self.name`; the agent-facing tool `name` stays `"web_search"` for both since that's unrelated to caching. Regression tests added in `test_tools.py`, including full `SearxngSearchTool` coverage (closing the §11.3 blind spot) and an explicit cache-key-namespace assertion per provider.

3. *(Minor)* **`tools/scraper.py:107` imports `nest_asyncio` directly, but it's only a transitive dependency** — present in `uv.lock` with no direct entry in `pyproject.toml`'s `dependencies`. If the upstream package pulling it in ever drops it, this import breaks silently with no lockfile signal pointing at `scraper.py` as the cause.

   **✅ Fixed (`ad529ea`).** Added `"nest-asyncio>=1.6.0"` to `pyproject.toml`'s `dependencies` and regenerated `uv.lock` (isolated diff — just the two `nest-asyncio` entries, no unrelated version churn). Full test suite verified green afterward (167 passed).

## 9. Observability & cost

1. **The Langfuse integration in `agents/crew.py:40-70` calls an API that doesn't exist in the pinned SDK version and will crash every run the moment it's turned on.** `_run_crew_node` does `lf.trace(name=..., user_id="system")` then `trace.span(name="run_crew")`. `pyproject.toml` pins `langfuse>=4.12.0`; confirmed directly against the installed package (`python -c "from langfuse import Langfuse; print(dir(Langfuse))"`) that the `Langfuse` class has no `trace` attribute at all in this version — v3+ replaced the old `.trace()`/`.span()` object model with OTEL-based `start_as_current_span`/`start_as_current_observation`. Today this is dormant because `get_langfuse()` (`utils/langfuse_utils.py:6`) returns `None` until `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` are set — and `.env.example:57-59` literally says "leave blank for V1" — but the `lf.trace(...)` call sits *before* the `try/except` that only wraps `crew.kickoff()` (`crew.py:57-62`), so as soon as someone follows the documented upgrade path and sets those two keys, every single crew node (research/analyse/write/edit) raises `AttributeError` before the agent even runs, taking down every run in the app. Needs to be rewritten against the current v4 tracing API, and covered by a test that actually instantiates a `Langfuse` client so this can't silently rot again.

   **✅ Fixed (`1f7041a`).** Rewritten against the real v4 API: `lf.start_as_current_observation(name=..., as_type="span")` as a context manager (`nullcontext()` standing in when Langfuse isn't configured, so the tracing calls are unconditional rather than duplicated per branch), `span.update(output=...)` on success and `span.update(level="ERROR", status_message=...)` on failure before re-raising. `test_langfuse_integration.py` instantiates a *real* `Langfuse` client (pointed at an unreachable host, so no network access needed) rather than mocking `get_langfuse()`, so a future SDK rename/removal fails the test instead of silently rotting again.

2. *(Minor)* **`get_redis_client()` (`utils/redis_client.py:31-38`) leaks the old connection pool on event-loop change.** When `current_loop is not _redis_loop`, it reassigns `_redis_client = redis.Redis.from_url(...)` without closing the previous client first. In production, with one event loop for the app's lifetime, this branch never fires. But the test suite (`tests/conftest.py:68-69`, `tests/test_redis_signaling.py:10`) creates a fresh loop per test, so each test that touches Redis silently leaks the prior test's connection pool instead of closing it.

## 10. Frontend

1. **A failed run's error reason never reaches the UI during a live session.** `app/runs/[id]/page.tsx`'s stream handler has an asymmetry: on `{ type: "complete" }` it calls `getRun(id).then(setRun)` to refresh the full run object before rendering, but on `{ type: "error" }` (`page.tsx:81-83`) it only does `setStatus("failed")` — it neither refetches `run` nor stores the `parsed.data.message` the backend actually sends. The backend emits real, specific messages for this event (`run_service.py:90,155,172,373`, e.g. `"HITL stage {status} timed out after 30 minutes."` or `"Run failed: {error_msg[:200]}"`), but the failed-state banner (`page.tsx:196-202`) reads `run.error_message` off the `run` object fetched at page-load time — which is `null` for a run that fails *during* the open session. The user sees a generic "This run failed. Check the agent logs above for details." with no reason, and only gets the real message if they manually reload the page (which triggers a fresh `getRun`).

   **✅ Fixed (`66dd1e5`).** Added a `runError` state set from `parsed.data.message` on the `"error"` stream event; the failed-state banner now renders `runError ?? run.error_message`, so a live failure shows the real backend message immediately while a reload still falls back to the DB-persisted value. Regression test added in `smoke.spec.ts`.

2. **`lib/hooks.ts`'s `useRunStream` is dead code that reimplements streaming incorrectly and would 404 if it were ever wired up.** It has zero call sites (only the working hand-rolled stream logic in `app/runs/[id]/page.tsx` is actually used) and does `new EventSource(\`/api/runs/${id}/stream\`)` — a relative Next.js API route that doesn't exist (`app/api/` only contains `auth/` and `backend-token/`, no `runs/` proxy). Even if that route existed, a native `EventSource` can't attach an `Authorization` header, which `page.tsx:87-89` explicitly calls out as the reason it uses `fetch` + manual SSE parsing instead. Since every backend endpoint requires the bearer JWT (`auth.py`), this hook could never have worked against the real backend. Safe to delete — keeping it around risks a future refactor "simplifying" `page.tsx` back to this broken pattern.

   **✅ Fixed.** Deleted `lib/hooks.ts`.

## 11. Tests

Several tests pass while validating the wrong thing — they exercise a mocked or hand-fed version of the behavior instead of the real code path, so they give false confidence over exactly the bugs already found in earlier sections.

1. **The cost-tracking tests never touch the code path that's actually broken.** `test_eval_and_cost.py::test_log_cost_writes_run_cost_row`/`test_log_cost_multiple_agents` and `test_analytics.py::test_costs_aggregates_run_costs` all call `log_cost(...)` (or insert `RunCost` rows) directly with hand-picked nonzero `total_cost` values like `0.05`/`0.01`/`0.02`. None of them go through `run_service._log_token_usages`, which is the only real caller of `log_cost` in production and hardcodes the argument to `0.0` (Backend services finding #1). The suite is 100% green on "cost tracking" while the feature it's meant to cover produces `$0.00` for every real run.

2. **The citation-extraction tests only feed `extract_citations` the internal RAG format, never the Markdown-link format the LLM pipeline actually outputs.** All four cases in `test_retrieval.py` (`test_extract_citations_parses_rag_output`, `_empty_on_no_sources`, `_deduplicates`, `_na_page`) construct input as `"SOURCE: <file> (Page: <N>)\n---\n..."` — exactly the internal `RAGTool._run` format, and exactly what Search/crawl-tools finding #1 identified as *not* what `configs/prompts.yaml`/`agents/writer.py` instruct agents to produce (`[Title](URL)` Markdown links). There's no test asserting `extract_citations` on realistic Markdown-cited research output, so the suite can't detect that citations come back empty for essentially every web-search-driven run.

3. **`SearxngSearchTool` — the primary new capability this whole change adds — has zero test coverage.** `test_tools.py` covers `TavilySearchTool` and `FirecrawlTool` in detail (success, cache hit, failure, empty-result fallback) but never imports or exercises `SearxngSearchTool` (confirmed via repo-wide grep — no test file references it). Consequently there's no test that could have caught the `web_search` cache-key collision between `SearxngSearchTool` and `TavilySearchTool` (Search/crawl-tools finding #2), nor any coverage at all of the self-hosted search path this diff is meant to introduce.

4. **No test asserts that a `"viewer"` workspace member is denied HITL approval — mirroring the exact gap in the code it's testing.** `test_access_control.py` and `test_runs.py::test_hitl_approve_requires_ownership` thoroughly cover *ownership* (stranger vs. owner vs. workspace member) but every membership fixture that reaches `POST /runs/{id}/approve` uses role `"operator"` or is the workspace owner — none uses `"viewer"`. Since `assert_run_access` ignores `role` entirely (Auth finding #1), a `"viewer"`-role test would fail today, but no test exists to say so — the coverage gap exactly tracks the code gap, so a naive "the tests pass" check gives no signal either way.

5. **`test_benchmark.py::test_benchmark_smoke` mocks out the exact two things — the LangGraph supervisor invocation and the HITL wait — that Agents finding #1 says are broken, so it cannot detect that bug, and its "quality bar" assertion is circular.** It patches `_invoke_supervisor_with_retry` with a fake that just merges hardcoded strings into state, and patches `_wait_for_hitl` to immediately return `"continue"` — so the real graph in `crew.py` never runs and the real HITL pause/resume flow is never exercised. The test then asserts `run.metrics["eval_scores"]["overall"] >= 70`, but `eval_scores` comes from `FAKE_EVAL_SCORES = {..., "overall": 81}`, a constant defined in the test file itself — the assertion can't fail unless someone edits the fake data. Despite the name and the `eval_set.md`/"benchmark" framing suggesting this guards output quality across prompt or model changes, it currently guards nothing about the agents, prompts, or HITL orchestration at all.
